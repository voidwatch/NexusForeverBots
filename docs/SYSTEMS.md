# Systems (non-PvP), status measured by bots

Status: done = implemented from tables/sources and exercised by a bot driver with evidence; partial = server code exists, the stated blocker (missing data or protocol messages) keeps part of it from being played;
todo = not implemented; blocked = no bot or script can exercise it (reason given). PvP (battlegrounds, arenas, warplots, rated PvP) is out of scope.

Bot drivers: `NF_BOTS_SYSTEMS` probes (`BOTS_SYSTEM_BOTS=n` in .env, code in Bots/BotSystems.cs) record `system-ok` / `system-fail` per probe in the failure report.
Other drivers: quest bots, `NF_BOTS_DUNGEON` (dungeon-check.sh), `NF_BOTS_EVENTS`. Client messages that reach the server without a handler are counted as `system-unhandled-message`.

Protocol note: the message enum in this repo (NexusForever.Shared/Network/Message/GameMessageOpcode.cs) has 361 opcodes; 118 client messages have a handler, 8 client
messages have a message class but no handler (ItemUseLootBag, MailTakeAllFromSelection, PlayerMovementSpeedUpdate, StorefrontPurchaseAccount/Character, plus transport messages).
Systems without any client message class here (tradeskill, friends, challenges, taxi, group loot roll pipeline, bank; trade and auction got theirs on 2026-10-05) cannot be driven through a real client
protocol here; the bot drivers call the server managers directly, which is the same code a handler would call. What is known about the missing messages without a client: docs/PROTOCOL.md.
2026-10-10: the Lua->opcode map now follows both client send functions (346 sending Lua functions); taxi, repair, matching queue, plugs, neighbours, friends by identity, group flags/markers and dye unlocks are driven through their real client messages; 34 Lua-reachable client messages remain without a handler (docs/OPCODE-COVERAGE.md).
